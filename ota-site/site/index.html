Developer trial · Alpha channel

Android for the curious car hacker.

Caramel Vanilla is a GMS-free Android Automotive build for Raspberry Pi 5. Bring a spare drive, a bench setup, and a willingness to poke at things.

This is intended for developers and DIYers interested in hacking around. It is not ready for prime time in a car yet. There are a great many things missing; we’ll add them over time.

!
Bench testing only

Do not use this build as the sole system in a road vehicle. It is a userdebug alpha, the A/B update path is experimental, and this release has not been validated as a production automotive system.

Why this is more than a plain AOSP checkout

Caramel Vanilla brings the missing glue.

Regular AOSP gives you the operating-system foundation. This build turns that foundation into a Raspberry Pi Automotive workbench with a deliberately opinionated set of hardware, app, and developer integrations.

01

Raspberry Pi 5 hardware profiles

Boot, kernel, fstab, display, PCIe/NVMe, SD-card, USB-audio, and Waveshare/HDMI integration are selected as reproducible product variants instead of hand-edited after boot.

02

Physical A/B updates

Duplicated boot, system, and vendor slots work with Android Update Engine, Pi tryboot, and a small boot-control service. Compact images can grow userdata to fill the drive after flashing.

03

Offline voice interaction

Caramel Voice provides push-to-talk recognition, a deterministic command layer, local speech models, and local speech synthesis. The current developer profile uses Zipformer recognition and Kokoro speech.

04

Automotive app surfaces

Car UI templates, a dock-style launcher, Car Settings install-source routing, and a parked-only Caramel Store make it possible to explore AAOS apps on a real Pi screen.

05

GMS-free app discovery

Caramel Store provides a signed, inspectable catalog path for the project’s repository; Aurora Store provides a separate open-source catalog experience. Installs remain explicit and user-controlled.

06

Navigation that fits AAOS

The packaged OsmAnd Automotive build includes a templates entrypoint alongside its full map UI, so navigation can participate in the car experience while parked testing remains available.

A/B update path

Update the inactive slot, then test it.

  1. Flash a fresh image first.Use a spare NVMe or SD card, then run expand-rpi5-userdata.sh from a Linux host.
  2. Verify the manifest.Check SHA-256 before writing a drive or applying a payload.
  3. Apply the OTA package.Extract the payload and properties, then use Android’s update_engine_client on the matching matrix variant.
  4. Keep a recovery path.The new slot gets one trial boot. Keep serial/bench access and a known-good image while testing.

Still alpha

  • Images are userdebug builds and permissive development software.
  • Do not treat the A/B path as an in-car safety system.
  • PCIe Gen 3 remains experimental on NVMe profiles.
  • Many vehicle integrations, validation tests, hardening tasks, and recovery workflows are still missing.

Read the machine-readable manifest and the source and build notes before trying anything.

Privacy · safety · expectations

Questions worth answering first.

Is this ready to use in a car?

No. It is a rough alpha userdebug build for developers and DIYers on a bench or spare drive. It is not a safety system, and it has not had production vehicle validation.

What leaves the device?

The public site itself has no sign-in, forms, analytics, or third-party scripts. On the device, network-capable apps such as map and app-catalog services may connect to their own services when you use them. Review each app’s settings and permissions before connecting it to a network.

Is voice processing local?

The captured developer profile uses local recognition and local speech synthesis. Treat this as a capability of the trial profile, not a blanket promise for every future model or command integration; inspect the build’s voice configuration before using it with sensitive audio.

What should I back up?

Back up anything on the target drive before flashing. Keep the original image, SHA-256 manifest, serial or recovery access, and a known-good bootable drive while testing the A/B path.

Where do I report a problem?

Start with the manifest issue tracker and include the exact matrix variant, image version, peripherals, and reproduction steps. Do not include private logs or credentials.
